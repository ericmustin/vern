Methodology

How Vern turns an OTLP sample into an Instrumentation Score, and which rules it checks.

How scoring runs

Each upload is decoded, shifted to the present, and loaded as its own isolated run into a self-managed Elasticsearch 9.5.5 on the free Basic license. Each rule from the Instrumentation Score spec runs as an ES|QL query against that run's data only. Vern computes the score from the results, then deletes the run's data. The ES|QL queries are public.

A rule query returns one result per service: whether the service passed, an extent (how much of its data the rule flagged) and an example of the evidence.

The formula

Score = Σ(Pi × Wi) / Σ(Ti × Wi) × 100

For each rule i, Ti is the number of services it checked and Pi the number that passed. Wi is the weight of the rule's impact:

ImpactWeight
Critical40
Important30
Normal20
Low10

A service's score uses only its own results; the overall score pools every service's results. Scores are shown with one decimal, and the category comes from the value shown: Poor below 50, Needs Improvement 50–74.9, Good 75–89.9, Excellent 90 and above.

Partial scores

A rule counts toward the score only if it was evaluated on your sample. Every other rule is left out of both sums and listed with the result, with its reason:

  • Not applicable: the sample has none of the signal the rule checks (for example, no metrics).
  • Not assessable: the sample cannot answer the question, for example because it covers too short a time.
  • Not implemented: Vern has no query for the rule yet, or the rule is opt-in.
  • Advisory: evaluated and shown for information, but not scored.
  • Error: the rule's query failed. The run is flagged as not trustworthy.

A partial score is computed from fewer rules than the spec defines, so compare it only with scores over the same rules.

Sensitive-data rules

Four rules look for sensitive data: RES-010 (resource attributes), SPA-006 (span names, status messages, span and span event attributes), LOG-003 (log bodies and attributes) and MET-008 (metric names, units and data point attributes). They need to know which fields your sample has, so they run only in vern score and vern serve. vern generate leaves them out of the workflow, and vern evaluate reports them not assessable.

Heuristic. Detection is best-effort pattern matching (email addresses, API keys and tokens, credit card numbers, US Social Security numbers, key=value secrets, and any non-empty value under a sensitive key name such as password or authorization). The spec's list is open-ended and no detector set is complete. Credit card numbers are matched by brand prefix and length, with no Luhn check. Placeholder values (masks such as ****, [REDACTED], ${ENV}, null) do not count. Nested maps and arrays are scanned, and several values of one attribute are joined before matching.

Redaction. Vern never copies a matched value into a report, an API response, the page or its logs. A failing rule shows the field, the kind of match and a masked preview. If an example from any other rule would contain a match, it is replaced with example withheld: it matches <kind>.

Blind spots. Vern lists what it could not scan. It counts:

  • keyword values longer than 1,024 characters (log bodies are scanned in full);
  • values cut to a rule's per-value limit, and fields or key names beyond the per-rule caps;
  • metric names that were dropped, and metric descriptions and exemplar attributes, which are not stored;
  • span events and log records with a zero or missing timestamp, which fall outside the scoring window;
  • long span status messages.

Some gaps are not counted, so a pass does not rule them out:

  • a malformed value under a key Elasticsearch types by name (for example a string that is not an IP under *.ip, or a bad *.timestamp) reads as null to the query;
  • attributes beyond Elasticsearch's 1,000-field mapping limit are not indexed, so they are not scanned.

Span events are told apart from log records by the missing observed_timestamp, which Elasticsearch's native OTLP ingest writes on log records only. SPA-006 scans the span events together with spans, and LOG-003 scans log records only.
